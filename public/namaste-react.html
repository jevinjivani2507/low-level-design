    Episode-01

    Inception

    In one breath: React is just JavaScript. React.createElement makes a plain object describing UI, and ReactDOM turns that object into real DOM inside one root node.

    ★The three APIs

    React.createElement(type, props, ...children)

    type: tag string like "h1" or a component.
    props: attributes object (or null).
    children: text, elements, or an array.

    Returns a React element, an object. Not a DOM node.

    ReactDOM.createRoot(domNode)

    Tells React “you own everything inside this node”. Returns a root with two methods: render and unmount.

    root.render(reactNode)

    Converts the element tree into DOM and puts it in the root. Existing children of #root get replaced. Returns undefined.

    ★Things the notes taught

    • React is an island. Divs above and below #root stay untouched, so React can be added to one part of an existing page.
    • Script order matters. Your script must run after the React and ReactDOM scripts, otherwise React is not defined.
    • “Not rendered yet” placeholder inside root makes it obvious when React failed to mount.
    • Props are passed to DOM as attributes: className (not class), style as an object. Unknown lowercase props like hello: "world" also land as attributes.
    • Multiple children go in an array, and arrays need key on each child.
    Interview gotcha
    Style keys inside createElement should be camelCase: backgroundColor. The notes wrote "background-color"; React warns about hyphenated style keys (CSS custom properties like --x are the exception).
    Fix in your notes: React 19 removed the UMD builds, so the unpkg.com/react@18/umd script pattern only works for React 18. Today you would use a bundler or an ESM CDN. Also, ReactDOM.render (pre-18 API) was removed in React 19; createRoot from react-dom/client is the only client root API.

    Igniting our App

    In one breath: React alone doesn't make an app fast. npm manages packages, and a bundler (Parcel) gives us a dev server, HMR, minification, tree shaking and code splitting.

    ★npm and the files it creates

    File / folderWhat it isCommit to git?
    package.jsonProject config + dependency ranges (^2.8.2)Yes
    package-lock.jsonExact installed versions + integrity hash of every package (incl. transitive)Yes, always
    node_modules/The actual code. Heaviest folder, regenerated with npm installNo
    dist/Parcel's build output (dev or production)No
    .parcel-cache/Parcel's cache so rebuilds are fastNo

    Rule of thumb: anything that can be regenerated goes in .gitignore.

    dependencies
    Needed when the app runs: react, react-dom, react-router-dom. npm i react
    devDependencies
    Needed only to build/test: parcel, jest, babel plugins. npm i -D parcel

    npm vs npx: npm installs and runs scripts; npx parcel index.html executes a package binary without a global install.

    ★What Parcel does for us

    HMR

    Hot Module Replacement swaps changed modules in the running page, often keeping state. Parcel's file watcher notices the change, cache keeps rebuilds in milliseconds.

    Tree shaking

    Removes exports you never import. Works because ES module import/export are static and analyzable at build time (CommonJS require is not).

    browserslist

    "browserslist": ["last 2 versions"] in package.json tells Babel/Parcel which browsers to support, so it knows how much to transpile and polyfill.

    ★Errors you met (and why)

    • Browser scripts cannot have imports or exports → add type="module" to the script tag loading App.js.
    • You are importing createRoot from "react-dom" → import from "react-dom/client".
    • Build fails because "main": "App.js" conflicts with an HTML entry → delete main from package.json.

    Transitive dependencies: your packages depend on other packages, forming a dependency tree. The lock file pins all of them.

    Fix in your notes: the tilde line reads "^2.8.2" twice; it should be "~2.8.2" → 2.8.2 up to < 2.9.0. And it's “zero config”, not “xero”. The “consistent hashing” point is better described as content hashing of output file names (index.cbf957bf.js) for long-term browser caching.
    SDE-2 context
    Create React App was officially deprecated by the React team in early 2025. In interviews, know the landscape: Vite (native-ESM dev server, fast), Webpack (most configurable, legacy-heavy), Parcel (zero config), and frameworks like Next.js or React Router (framework mode) that ship their own build.

    Episode-03

    Laying the Foundation

    In one breath: JSX is HTML-like syntax that Babel compiles into createElement calls. A functional component is just a function that returns JSX.

    ★npm scripts

    ★The JSX journey

    JSX is not HTML
    • className, htmlFor, camelCase events (onClick)
    • Every tag must close: <img />
    • { } embeds a JS expression (not a statement)
    • JSX is separate from React; React just uses it
    Babel

    A JS compiler/transpiler: JSX → JS, and modern syntax → older syntax per browserslist. Missing APIs get polyfills (e.g. core-js) — replacement implementations of features old browsers lack.

    Safety (sanitization)

    Values inside { } are escaped before insertion, so {userInput} can't inject a script. The escape hatch dangerouslySetInnerHTML is named that way on purpose.

    ★Functional components

    Component composition = building a component out of other components. That's the whole React mental model: small pieces, nested.

    Interview gotcha: <Title /> vs {Title()}
    <Title /> creates an element; React calls the function, gives it its own spot in the tree, its own state and hooks. {Title()} just runs the function inline: its hooks become the parent's hooks, and React can't bail out of rendering it separately. Use the tag.
    Fix in your notes: capitalizing a component name is required, not just good practice. In JSX, lowercase <title /> compiles to the string "title" (an HTML tag); capitalized <Title /> compiles to a reference to your function. Also, since React 17's automatic JSX runtime, you don't need import React just to write JSX.
    Fix in your notes: Parcel does not strip console.log by default (your notes caught this). Use babel-plugin-transform-remove-console in .babelrc, with {"exclude": ["error","warn"]} to keep errors and warnings.

    Episode-04

    Talk is Cheap, Show me the Code

    In one breath: We start Food Villa. Props pass data down, map() renders lists, keys let React's diffing algorithm match old and new items, and Fiber is the engine doing that work.

    ★The app we're building

    ★Fragments and one parent

    A component returns one JSX expression because JSX compiles to one createElement call, and a function can only return one value. Wrapping in a <div> adds a useless DOM node; a fragment doesn't.

    ★Styling in JSX

    Inline style
    style={{ backgroundColor: "red" }}
    Outer braces = JS, inner braces = object. camelCase keys, commas not semicolons.
    External CSS
    className="card" + rules in a .css file. Preferred for anything non-trivial (later: Tailwind, CSS modules).

    ★Props

    Props are arguments to a component. React collects all attributes into one object and passes it as the first parameter. They flow parent → child only and are read-only inside the child.

    Optional chaining res?.info?.name returns undefined instead of throwing when something in the chain is null/undefined. Essential with API data.

    Config-driven UI: the backend sends data describing what to show (which carousels, offers, layout per city) and the UI renders whatever the config says. Swiggy's home page works this way.

    ★Virtual DOM, diffing and keys

    Diffing heuristics (O(n))
    • Different element type → throw away subtree, build new.
    • Same type → keep node, update changed attributes.
    • Lists → match children by key.

    Generic tree diff is O(n³); these two assumptions make it O(n).

    Key choices
    • ✓ Stable unique ID from data (res.info.id)
    • ~ Index: only for static lists that never reorder/filter
    • ✗ Math.random() / shortid.generate() inside render
    Fix in your notes: key={shortid.generate()} inside map creates a new key every render, so React unmounts and remounts every card each time (lost state, wasted work). Generate IDs once when data arrives, or use the API's ID.
    React Fiber (React 16+)

    A rewrite of the reconciler. Each component instance becomes a fiber node, a unit of work. Rendering can be split into chunks, paused, prioritized, resumed or thrown away, while the commit stays synchronous. React keeps two trees (current and work-in-progress) and swaps them on commit. This is what makes concurrent features (transitions, Suspense) possible.

    In one breath: Render something immediately, then fetch data in useEffect, show a shimmer while waiting, and re-render when the data arrives.

    ★Two ways to load a page

    Fetch → render
    Call API (300ms), then render (200ms). User stares at a blank screen for 500ms.

    Episode-07

    Finding the Path

    In one breath: react-router-dom maps URLs to components. Nested routes render into an Outlet, dynamic segments are read with useParams, and Link navigates without reloading.

    ★Rules of hooks (and why)

    Never
    • call hooks inside if, loops, or nested functions
    • call hooks outside a component / custom hook
    • define a component inside another component
    Why

    React stores hook state as an ordered list on the fiber and matches them by call order each render. Skip one conditionally and every later hook gets the wrong state.

    A component defined inside another is a new function each render, so React sees a different type, unmounts it and loses its state.

    Images: import local files from src/assets (import logo from "../assets/logo.png"), but production apps like Swiggy serve images from a CDN (Cloudinary): cached at the edge, optimized per device, high uptime.

    ★The route tree

    Server-side routing
    Every URL change asks the server for a new HTML document. Full reload, state lost.
    Client-side routing (SPA)
    All components already shipped; the router updates the URL with the History API and swaps components. No document request.

    Link vs <a>: <Link> renders an <a> in the DOM but intercepts the click and calls history.pushState, so the page doesn't reload. A raw <a href> reloads everything.

    Shimmer keys
    For a fixed list of skeleton cards, key={index} is fine: the list never reorders or changes identity.
    Fix in your notes: the line says “If we load a path that has been defined…” → should be “not defined” for the 404 error page. Also React Router v7 merged packages: new code can import everything from "react-router"; react-router-dom still works as a re-export. Use <Route index> / { index: true, element: <Body/> } for the default child.

    Episode-08

    Let's get Classy

    In one breath: Class components are the older way. Know their lifecycle (render phase vs commit phase), how setState works, and why cleanup matters in an SPA.

    ★Class vs function, side by side

    this.setState({ count: 1 })
    Shallow-merges into the state object; other keys are kept. Never write this.state.count = 1.
    setCount(1)
    Replaces the value. For an object state you must spread: setUser(u => ({...u, name})).

    ★The lifecycle diagram (mounting is the must-know)

    Predict the order: parent class with two class children
    Reveal
    1. Parent constructor
    2. Parent render
    3. First constructor
    4. First render
    5. Second constructor
    6. Second render
    7. — one batched DOM commit —
    8. First didMount
    9. Second didMount
    10. Parent didMount

    React finishes the render phase for the whole subtree first (cheap), then does one commit (expensive DOM work), then runs didMounts children first, because a parent is only “mounted” once its children are. If a child's didMount is async, anything after its await logs after “Parent didMount”.

    ★Cleanup: the SPA trap

    Navigating away in an SPA doesn't reload the page; it just unmounts components. An interval started on mount keeps running. Come back and you have two intervals, then three…

    Why not useEffect(async () => …)?
    An async function always returns a Promise. React expects the effect to return a cleanup function or nothing. Define an async function inside and call it.
    Fix in your notes: componentDidUpdate is not called after the initial render; it only runs after updates. So it's not “like an empty dependency array” — componentDidMount is the closest to [], and componentDidUpdate + prev-value checks is the closest to [deps]. And as the notes say: don't map lifecycles 1:1 to hooks. Effects are about synchronizing with something external, not about moments in time.
    Still class-only in 2026

    Error boundaries: static getDerivedStateFromError() + componentDidCatch(). No hook equivalent; libraries like react-error-boundary wrap a class for you. They catch errors during rendering and lifecycles, not in event handlers or async code.

    Episode-09

    Optimizing our App

    In one breath: Pull stateful logic into custom hooks (single responsibility), and split the bundle so users only download code for the page they open.

    ★Custom hooks

    A custom hook is a function whose name starts with use and that calls other hooks. It reuses logic, not state: two components calling useOnlineStatus() each get their own state.

    • Readable, reusable, maintainable, testable.
    • Live in src/utils/ (or hooks/), file named useSomething.js, named export preferred.

    The component shrinks to: const resInfo = useRestaurantMenu(resId); if (!resInfo) return <Shimmer/>; Rendering and fetching are now separate concerns.

    Fix in your notes: a custom hook isn't a “child component”. Its state lives on the component that calls it, so when the hook's state changes, the calling component re-renders (and its children). Also initialize with navigator.onLine rather than true, so a page that loads offline shows the right status.

    ★Code splitting with lazy + Suspense

    Also called chunking, dynamic bundling, lazy loading, on-demand loading, dynamic import. One giant bundle means users download Instamart's code even if they never open it.

    • import() returns a Promise. Without Suspense, React has nothing to render while it's pending and throws.
    • lazy expects a module with a default export. For a named one: lazy(() => import("./X").then(m => ({ default: m.X }))).
    • Never call lazy() inside a component: a new lazy component each render means remount and state loss.
    • Split by route first (biggest win), then by heavy widgets (charts, editors, maps).

    Beyond the course

    Frontend security

    In one breath: never trust anything that crosses a boundary. Encrypt the pipe (HTTPS), treat every input as hostile and encode every output for its context (XSS), make sure requests are really intended (CSRF), keep tokens where scripts can't steal them, and tell the browser your rules with headers (CSP, HSTS, frame-ancestors).

    ★HTTPS: what the padlock really means

    TLS gives you three things: encryption (nobody on the Wi-Fi can read it), integrity (nobody can change it in transit) and authentication (the server proved it owns the domain via a certificate). It does not make your app secure; it only secures the pipe.

    MITM + HSTS

    An attacker on the network can downgrade http:// links before the redirect to HTTPS happens. Strict-Transport-Security tells the browser to use HTTPS only for this domain from now on. The very first visit is still exposed, which is why the HSTS preload list exists.

    mixed content

    An HTTPS page loading HTTP scripts or iframes. Browsers block active mixed content and upgrade or flag images. One HTTP script can rewrite the whole “secure” page.

    ★Same-origin policy and CORS (deeper than Ep 6)

    An origin is protocol + host + port. Scripts can freely send many cross-origin requests, but can only read the response if the server opts in with CORS headers.

    Simple request (no preflight)

    GET, HEAD or POST, only safelisted headers, and Content-Type is form-urlencoded, multipart or text/plain. Sent straight away; the browser just checks the response headers.

    Preflighted request

    PUT/DELETE/PATCH, custom headers like Authorization, or application/json. The browser first sends OPTIONS; cached with Access-Control-Max-Age.

    Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Vary: Origin

    With credentials the origin must be exact, never *. Vary: Origin stops a cache serving one origin's answer to another.

    Trick question alert
    “Does CORS protect my API?” No. CORS is enforced by browsers to protect users. curl, Postman and server code ignore it. And simple requests still reach your server and change data even when the response is blocked, so CORS is not CSRF protection either.

    ★XSS: the most-asked topic

    Cross-site scripting means an attacker's JavaScript runs on your origin. From there it can read the DOM and localStorage, call your APIs as the user, and fake login forms.

    stored

    The payload is saved on the server (a comment, a username) and served to every visitor. The most damaging kind.

    reflected

    The payload is in the URL (?q=<script>) and the server echoes it into the page. The victim has to click a crafted link.

    DOM-based

    Never touches the server: client JS reads location.hash or postMessage data and writes it into a sink like innerHTML.

    React escapes everything inside {}, so most XSS questions become “where can it still leak?”

    Defense in depth: encode output by default (React does), sanitize the rare HTML you must render (DOMPurify), validate URL protocols, add a strict CSP so an injected script still can't run, and keep tokens in HttpOnly cookies so a successful XSS can't steal them.
    Spot the hole
    Reveal

    DOM-based XSS. ?q=<img src=x onerror=alert(document.cookie)> runs code. (A plain <script> tag won't execute via innerHTML, but event-handler attributes do.)

    Fix: textContent instead of innerHTML, or render it through JSX.

    ★Authentication, authorization and tokens

    Authentication: who are you?

    Login, passwords, OTP, OAuth/SSO. Failure is 401 Unauthorized (the name is misleading: it means “not authenticated”).

    Authorization: what may you do?

    Roles, permissions, ownership checks. Failure is 403 Forbidden. Must happen on the server for every request.

    Session cookie

    Server stores the session, browser holds an ID. Easy to revoke (delete the session). Sent automatically, so it needs CSRF protection.

    JWT

    header.payload.signature, base64url-encoded, not encrypted: anyone can read the payload. Stateless and easy to scale, but hard to revoke before expiry, so keep it short-lived.

    ★CSRF: the request you didn't mean to send

    defenses
    1. SameSite cookies (Lax or Strict), set explicitly rather than relying on browser defaults.
    2. CSRF token: a random value the server issues and checks on every state-changing request (synchronizer token, or double-submit cookie).
    3. Check the Origin / Referer header on the server.
    4. Never change state with GET. Require a custom header (like X-Requested-With) or JSON, which forces a preflight that evil.com can't pass.

    XSS vs CSRF in one line: XSS runs the attacker's code on your site; CSRF makes the user's browser send a request to your site from somewhere else. If you have XSS, CSRF tokens don't save you, because the script can read the token.

    ★Iframes: clickjacking and postMessage

    your site inside their frame

    Clickjacking: the attacker loads your page in an invisible iframe over a “Win a prize” button, so the user really clicks your “Delete account”. Fix with frame-ancestors 'none' (or 'self') in CSP, plus X-Frame-Options for old browsers.

    their frame inside your site

    Use sandbox to strip powers, then add back only what's needed (allow-scripts, allow-forms). Never combine allow-scripts + allow-same-origin for same-origin content: the frame can remove its own sandbox.

    Related: target="_blank" links used to give the new tab window.opener access (reverse tabnabbing). Modern browsers imply rel="noopener" now, but writing it explicitly is still a good answer.

    ★SRI: trusting a CDN without trusting it

    If one byte of the file changes (CDN hacked, file swapped), the browser refuses to run it. Needs an exact pinned version, and crossorigin="anonymous" so the browser can check a cross-origin file. Real example: in 2024 the polyfill.io domain changed owners and started serving malicious code to the sites that loaded it. It generated different code per browser, so it couldn't be pinned with SRI at all: the lesson is to self-host or pin scripts you don't control.

    ★Server-side ones a frontend dev should know

    These show up because frontend engineers now write Node, Next.js API routes and backend-for-frontend layers.

    SSRF

    Server-Side Request Forgery: your server fetches a URL the user controls, like a link-preview route /api/preview?url=. The attacker passes http://169.254.169.254/ (cloud metadata with credentials) or http://localhost:6379.

    Fix: allowlist hosts, resolve DNS and block private IP ranges, don't follow redirects blindly, set timeouts.

    SSJI

    Server-Side JavaScript Injection: user input executed as code in Node. Sinks: eval, new Function, setTimeout("string"), the vm module (not a security sandbox), Mongo $where.

    Fix: never execute input. Use JSON.parse, a safe expression parser, and type-check inputs so {"$gt": ""} can't sneak into a query.

    ★The “much more” list

    • Secrets in env vars: anything prefixed VITE_, NEXT_PUBLIC_ or REACT_APP_ is baked into the bundle and public. Real secrets stay on a server; the browser calls your backend, which calls the third party.
    • Supply chain: commit the lock file, run npm audit, use Dependabot/Renovate, review new dependencies, prefer npm ci in CI.
    • Open redirect: /login?next=https://evil.com. Allow only relative paths or an allowlist of hosts.
    • Prototype pollution: a naive deep merge of {"__proto__": {"isAdmin": true}} adds isAdmin to every object. Skip __proto__/constructor keys, use Object.create(null) or Map.
    • Sensitive data in the client: don't trust hidden fields, prices or roles sent from the browser; the server recomputes them.
    • Rate limiting and brute force on login and OTP endpoints, with a generic “invalid email or password” message so you don't reveal which accounts exist.

    ★Scenario round

    a typical senior question

    “You're building a comment section that supports bold, italics and links. Walk me through every security concern.”

    what scores points

    ★Hydration, and when it fails

    Hydration is React taking server-rendered HTML and attaching to it: it renders the same tree in the browser, matches it to the existing DOM nodes instead of recreating them, and wires up event handlers. Done with hydrateRoot. React 18 added selective hydration: with Suspense boundaries, parts hydrate independently and the part the user clicks gets priority.

    causes of mismatches
    • Date.now(), new Date(), Math.random() during render
    • Reading window, localStorage, screen size during render
    • Locale or timezone differences between server and browser
    • Invalid HTML nesting (<div> inside <p>), which the browser silently “fixes”
    • Browser extensions injecting markup
    fixes
    • Render the client-only value in useEffect after mount (two-pass render)
    • useId for IDs, not counters or random numbers
    • Load client-only components lazily (Next.js: dynamic(..., { ssr: false }))
    • suppressHydrationWarning for one unavoidable text difference, like a timestamp

    Why it matters: on a mismatch React throws away the server HTML for that part and re-renders it on the client, losing the SSR performance gain and possibly causing a visible flash.

    ★The event loop

    Key consequences: a microtask that keeps scheduling microtasks starves rendering (the page freezes), while setTimeout(fn, 0) always waits for the current task and every pending microtask. Web APIs (timers, fetch, DOM events) run outside the JS thread and only queue the callback.

    Output order?
    Reveal

    1, 5, 7, 3, 4, 6, 2. Synchronous code first: 1, then the async function runs synchronously up to its first await (5), then 7. Microtasks in the order they were queued: 3, 4, then the code after await (6). The timer is a new task, so 2 comes last.

    ★Breaking up long tasks

    Any task over 50 ms is a “long task”: clicks and keystrokes wait behind it, which hurts INP. Fixes, from simplest:

    • Yield to the main thread regularly so input and rendering can run in between (below).
    • Web Workers for pure computation (parsing, image processing, search indexes). No DOM access; talk via postMessage.
    • React: useTransition / useDeferredValue so heavy re-renders become interruptible; list virtualization so you render 20 rows, not 10,000.
    • requestIdleCallback for non-urgent work like analytics.

    ★Event delegation

    Events go through three phases: capture (window down to the target), target, then bubble (back up). Delegation uses bubbling: put one listener on a parent instead of one per child. Fewer listeners, less memory, and it works for children added later.

    • e.target is what was actually clicked; e.currentTarget is the element the listener is on.
    • stopPropagation() stops bubbling; preventDefault() stops the browser's default action (link navigation, form submit). They're independent.
    • focus/blur and mouseenter/mouseleave don't bubble; use focusin/focusout and mouseover/mouseout for delegation.
    • React itself delegates: since React 17 it attaches one listener per event type to the root container.

    ★Garbage collection, memory leaks, WeakMap

    JavaScript uses mark-and-sweep: starting from roots (globals, the current call stack), mark everything reachable; whatever isn't marked is freed. Cycles are fine as long as nothing reachable points into them. V8 is generational: most objects die young, so new objects are collected often and cheaply, survivors move to an old space collected less often.

    A memory leak in JS is memory that's still reachable but no longer needed.

    usual suspects
    • setInterval and listeners never cleared
    • Subscriptions (sockets, stores, emitters) without unsubscribe
    • Detached DOM nodes removed from the page but still referenced in a JS variable
    • Closures holding large objects longer than needed
    • Caches and arrays that only grow
    • Accidental globals (assigning to an undeclared variable)
    • React: effects without cleanup, setState on unmounted components after slow fetches
    how to find them
    1. DevTools Memory tab: take a heap snapshot, do the action several times, take another, compare.
    2. Filter the snapshot by “Detached” to find removed DOM nodes still held in memory.
    3. Performance monitor: JS heap size and DOM node count should come back down, not climb steadily.
    4. Read the retainers path to see which reference keeps the object alive.
    MapWeakMap
    KeysAnythingObjects only (and non-registered symbols)
    Holds keysStrongly: keeps them aliveWeakly: if nothing else references the key, the entry disappears
    Iterable, sizeYesNo (contents depend on when GC runs)
    Use forGeneral key-value dataExtra data attached to objects you don't own: metadata per DOM node, per-object caches, private data

    Related: WeakSet (mark objects as seen), WeakRef and FinalizationRegistry (rarely needed, behavior depends on GC timing).

    ★Babel and tree shaking

    Babel works in three steps: parse code into an AST, transform the AST with plugins (presets are bundles of plugins: preset-env, preset-react, preset-typescript), and generate code plus source maps. preset-env reads browserslist to decide what to transpile; with core-js and useBuiltIns: "usage" it adds only the polyfills your code uses. SWC and esbuild do the same job much faster and are now common defaults.

    Tree shaking drops unused exports. It needs ES modules (static import/export), works best with "sideEffects": false in package.json (so the bundler can drop whole unused files), and the minifier removes the dead code at the end. Things that defeat it: CommonJS require, modules with side effects on import, and importing a whole library (import _ from "lodash" instead of import debounce from "lodash/debounce").

    ★React Fiber, deeper

    what a fiber is

    A JS object per component instance or element: its type, props, state, effects, and pointers to child, sibling and return (parent). That linked structure lets React walk the tree in a loop and pause between units of work, which a recursive call stack couldn't.

    double buffering

    React keeps the current tree (on screen) and builds a work-in-progress tree. When the work-in-progress tree is complete, commit swaps them. An interrupted render just throws the unfinished tree away.

    priorities (lanes)

    Updates get a priority: typing and clicks are urgent, transitions and data loading aren't. React can pause a low-priority render to handle an urgent one, then resume or restart it. That's what powers useTransition and Suspense.

    Render phase: interruptible, must be pure (it may run more than once). Commit phase: synchronous, applies DOM changes, then runs layout effects and schedules effects.

    ★Context API

    • Every consumer re-renders when the value changes by Object.is. Passing {{ theme, setTheme }} inline creates a new object every render, so all consumers re-render every time App does. Memoize it.
    • Split contexts by how often they change (theme vs current user vs cart), or put state and setters in separate contexts.
    • Context isn't a state manager; it's a way to pass a value down. For frequently changing shared state, a store with selectors (Redux, Zustand) avoids re-rendering everyone.
    • React 19: <ThemeContext value={...}> works as the provider directly, and use(ThemeContext) can be called conditionally.

    ★Cascade, specificity, inheritance

    When several rules set the same property on an element, the cascade picks the winner by checking these in order and stopping at the first difference:

    1. Origin and importance: browser defaults < your styles; !important flips the order so important declarations win.
    2. Cascade layers (@layer): later layers beat earlier ones; styles not in any layer beat all layers.
    3. Specificity of the selector.
    4. Order of appearance: the later rule wins.
    SelectorSpecificity (IDs, classes, elements)
    p0, 0, 1
    .card p0, 1, 1
    ul li::before0, 0, 3 (pseudo-elements count as elements)
    #nav .link:hover1, 2, 0 (pseudo-classes and attributes count as classes)
    :where(#nav) p0, 0, 1 (:where() always adds zero)
    :is(#nav, .menu) p1, 0, 1 (:is() and :not() take their most specific argument)
    style="..."Beats any selector; only !important beats it

    Compare left to right like version numbers: one ID beats any number of classes. * and combinators (>, +, ~) add nothing.

    Inherited by default

    Mostly text-related: color, font-*, line-height, text-align, visibility, cursor, list-style.

    Not inherited

    Mostly box-related: margin, padding, border, background, width, height, display, position.

    Control it with inherit (take the parent's value), initial (the CSS spec default), unset (inherit if the property normally inherits, else initial) and revert (back to the browser's default style). An inherited value always loses to any rule that targets the element directly, however weak its selector.
